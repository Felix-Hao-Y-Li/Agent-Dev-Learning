# review — 教师批改模式

用户自己写了代码或撞到了报错。你的任务不是挑 bug 清单，而是像老师批改作业一样：告诉他哪里对、哪里过时、为什么，然后**把改好的完整代码给他**。

## 步骤

### 1. 读代码 + 版本自检
读用户指定的文件（没指定就问是哪个）。同时读同目录的 `pyproject.toml` 确认实际装的版本 —— 很多"报错"其实是版本不匹配。

### 2. 查权威源
按 `.claude/skills/_shared/sources.md` 的顺序查证现行推荐写法。**不要凭记忆判断某个写法过不过时**，该文件第三节的过时清单本身也需要重查。

### 3. 输出五段

**① 能不能跑通 / 报错根因**
如果有报错，定位到具体是哪一行、哪个参数、哪个版本变更导致的，说清因果链，而不是只说"这里要改成 X"。能实际跑一下就跑一下（`uv run`），用真实输出说话。

**② 写法是否已是现行推荐**
对照官方文档现行写法逐点说明。每个判断都给出文档依据（页面路径或链接 + 查证日期）。区分三种情况说清楚：
- 写错了（跑不通）
- 能跑通但已废弃（官方标了 deprecated）
- 能跑通也没废弃，只是有更好的写法

**③ 直接给出改好的完整代码**
这是强制项。**不能只说"建议改成 X"或给片段** —— 给出完整的、可以直接替换原文件的版本，**逐行中文注释并按 `_shared/code-comments.md` 分级**（`[核心]` / `[了解]` / `[脚手架]` + 文件头阅读地图），改动过的地方额外注明「原来是什么、为什么改」。改动本身默认算 `[核心]`。改完实际跑一遍验证。

**④ 流程图**
给完改好的代码就画一张 Mermaid `flowchart`，画的是**这段代码实际的执行流程**（节点对应到具体函数或 API 调用，边上标数据形态，10 个节点以内）。改动改变了流程走向时，把变化点在图上标出来。详细要求见 `learn/SKILL.md` 第 5 段。

**⑤ 面试官会追问什么**
基于这段代码，列 2-3 个面试官大概率会追问的点，附回答要点。这是把练习代码转成求职资本的一步。

## 边界

- 中文输出，代码注释也用中文。
- 不生成计划，不改 `study-log/`，不勾选 checkpoint。
- 用户写得对的地方要明确说对，不要为了凑批改意见硬找问题。
- 只指出与本次代码相关的问题，不扩散到整个项目的重构建议。
- 新建/修改的代码文件遵守仓库 CRLF 约定。
